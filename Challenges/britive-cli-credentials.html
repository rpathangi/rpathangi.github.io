Challenge

Streamlining AWS CLI Access with Britive

Goal: Eliminate repetitive manual credential checkout from Britive when running AWS CLI commands. After this one-time setup, every aws, terraform, or SDK command automatically fetches fresh credentials in the background using credential_process.

Part 1

Human / Interactive Access

For developers running the AWS CLI, Terraform, or SDKs from their own terminal.

Prerequisites

  • AWS CLI v2 installed - verify with aws --version
  • Python 3.8+ installed - verify with python --version
  • Access to a Britive profile for the target AWS account (confirm with your Britive administrator)
  • Network connectivity from your terminal to the Britive API endpoints
1

Install PyBritive

bash
pip install britive

Verify the installation:

bash
pybritive --version
2

Authenticate PyBritive (one-time)

Run the interactive configuration:

bash
pybritive configure

You will be prompted for:

  • Tenant URL - your Britive tenant (for example, https://your-tenant.britive-app.com)
  • Authentication method - select the SSO method your organization uses

This stores your authentication config locally. You only need to do it once.

3

List available profiles

See which AWS profiles you can check out:

bash
pybritive ls profiles

Identify the profile for your AWS account. It will look something like:

example output
My Org AWS/123456789012 (dev)/Developer-Access
4

Create a profile alias

Aliases simplify the config and reduce latency on each credential fetch:

bash
pybritive checkout "My Org AWS/123456789012 (dev)/Developer-Access" --alias aws-dev

Note

Replace the profile path with your actual profile from Step 3. The alias aws-dev is a short name you'll reference going forward.

5

Configure the AWS CLI to use credential_process

Edit (or create) your AWS config file:

  • Windows: C:\Users\<YourUsername>\.aws\config
  • Linux / macOS: ~/.aws/config

Add the following profile entry:

ini
[profile aws-dev]
credential_process = pybritive-aws-cred-process --profile aws-dev
region = us-west-2

What this does

Every time the AWS CLI needs credentials for the aws-dev profile, it calls pybritive-aws-cred-process, which checks out from Britive, returns temporary credentials as JSON, and the CLI uses them transparently. When they expire, the CLI calls the process again - no manual intervention.

6

Verify it works

Run any AWS command using the profile:

bash
aws sts get-caller-identity --profile aws-dev

You should see your assumed role ARN and account ID - without having opened the Britive UI or manually checked out. To make this the default for the terminal session:

Windows (PowerShell)
$env:AWS_PROFILE = "aws-dev"
Linux / macOS
export AWS_PROFILE=aws-dev

Now all commands use this profile automatically:

bash
aws s3 ls
aws kinesis list-streams
terraform init
terraform apply
7

Enable auto-renewal for long-running scripts

If you run scripts that take longer than your credential TTL, use --force-renew:

bash
pybritive checkout aws-dev --mode integrate --force-renew 15

This checks whether credentials expire within 15 minutes and auto-refreshes them if so.

Note

When using credential_process (Step 5), the AWS CLI handles renewal automatically by re-invoking the process command. --force-renew is only needed for integrate mode (writing to ~/.aws/credentials directly).

Part 2

Machine / Automated Access

For an unattended workload that accesses AWS without human interaction.

1

Request a service identity from your Britive admin

Ask your Britive administrator for:

  • A service identity (non-human) for the workload
  • Scope limited to only the AWS resources the workload needs (for example, S3, Kinesis, a specific IAM role)
  • A service identity token, which the admin will generate

Reference: Britive Service Identities guide.

2

Store the token securely

Store the service identity token in a secret manager:

  • AWS Secrets Manager
  • Azure Key Vault
  • HashiCorp Vault
  • Or your organization's approved secret store

Never store secrets in the clear

Do not store the token in source control, environment files, or plain-text config.

3

Fetch credentials programmatically

In your workload code (Python example):

python
import requests
import boto3

# Retrieve the token from your secret manager
SERVICE_TOKEN = get_secret("britive-pipeline-token")

# Call the Britive API to check out programmatic credentials
headers = {"Authorization": f"TOKEN {SERVICE_TOKEN}"}
response = requests.post(
    "https://your-tenant.britive-app.com/api/v1/profiles/<profile-id>/checkout",
    headers=headers,
    json={"accessType": "PROGRAMMATIC"},
)
creds = response.json()

# Use the credentials with boto3
session = boto3.Session(
    aws_access_key_id=creds["accessKeyId"],
    aws_secret_access_key=creds["secretAccessKey"],
    aws_session_token=creds["sessionToken"],
)
s3 = session.client("s3")

Reference: Britive Programmatic Checkout API.

4

Implement credential rotation

Add logic to refresh credentials before they expire:

python
from datetime import datetime, timedelta, timezone

def get_or_refresh_credentials(current_creds, expiry_time):
    """Refresh credentials if they expire within 5 minutes."""
    buffer = timedelta(minutes=5)
    if datetime.now(timezone.utc) + buffer >= expiry_time:
        return checkout_new_credentials()
    return current_creds
