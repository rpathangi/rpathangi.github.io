Complete starter prompt — copy entire block
/aidlc Build a minimal, self-contained AWS CDK app in TypeScript that is a working proof-of-concept for multi-tenant SaaS application-level audit logging. It captures a SaaS application's own domain audit events, attributes each to an actor and a tenant, delivers them reliably and decoupled from the request path, stores them immutably (append-only, WORM) in S3, enforces per-tenant isolation of the audit trail, and makes events searchable per tenant. The sample domain is a regulated analytical lab with a single Sample entity. The full build specification follows below - treat it as the authoritative detail for every stage.

STAGE-GATED DELIVERY
Use a human-approved, stage-gated workflow. At the end of each stage, present assumptions, decisions, risks, generated artifacts, validation evidence, and open questions, then stop for explicit approval before continuing.

1. Requirements and threat-model stage: confirm every project variable; define trust boundaries, tenant and administrator authorization, data classification, abuse cases, retention obligations, control mappings, evidence requirements, cost constraints, and success criteria.
2. Architecture and design stage: produce the stack boundaries, data flows, event contract, IAM/KMS/S3/Athena/AOSS isolation design, failure modes, and teardown/RETAIN plan. Do not implement until approved.
3. Implementation stage: generate the minimal self-contained CDK TypeScript project and application code described below. Pin every dependency to an exact version and explain each package.
4. Verification stage: run local type checks, tests, CDK assertions or snapshots, and synthesis; demonstrate tenant-isolation policy tests and explain any validation that requires a deployed environment.
5. Deployment-readiness stage: show the synthesized changes, permissions, costs, Object Lock consequences, rollback limitations, and production-hardening gaps. Do not run cdk deploy.
6. Optional deployment and demo stage: proceed only after explicit confirmation from the owner of the named target AWS account. Run the demo walkthrough only after an approved deployment.

GOAL AND SCOPE
Build a minimal, self-contained AWS CDK TypeScript proof of concept for multi-tenant SaaS application-level audit logging. The sample domain is a regulated analytical lab with one Sample entity. Generate code and documentation; do not claim that resources exist before an authorized deployment succeeds.

IDENTITY, API, AND DATA MODEL
- Create an Amazon Cognito User Pool identity model with a custom tenantId claim and the Cognito sub claim as the actor identifier.
- Protect Amazon API Gateway with a Cognito authorizer.
- Implement a Sample Lambda and a DynamoDB Samples table with partition key tenantId and sort key sampleId.
- Derive tenant and actor only from validated JWT claims. Never accept tenantId or actorId from the request body or other client-controlled fields.
- Keep the application-layer tenant check even when infrastructure policies also enforce isolation.

SAMPLE LIFECYCLE AND CONTROL BEHAVIOR
Support these operations: SUBMIT, ACQUIRE, REPROCESS, REVIEW, APPROVE, SIGN, GET, UPDATE, DELETE.

Reject applicable data-altering operations without a reason for change with HTTP 422. For this POC, REPROCESS and UPDATE require reasonForChange. Treat this as this POC template's design/control requirement mapped by the project to 21 CFR Part 11, not as a blanket legal determination. Validate the project-specific rules for any other operation during the requirements stage.

After each successful DynamoDB write, emit exactly one custom EventBridge bus audit event. Do not emit an audit event for a failed write. Make retries and idempotency behavior explicit so one successful logical write has exactly one corresponding event. The contract supports GET; during the requirements stage, document and approve the read-audit behavior separately from the after-write guarantee.

EXACT AUDIT EVENT CONTRACT
Use this exact shared event contract:
{
  "eventId": "uuid-v4",
  "eventVersion": "1.0",
  "timestamp": "ISO-8601, server-set, never client-supplied",
  "tenantId": "from JWT claim (lab site)",
  "actorId": "from JWT sub claim (analyst)",
  "actorType": "user | admin",
  "operation": "SUBMIT | ACQUIRE | REPROCESS | REVIEW | APPROVE | SIGN | GET | UPDATE | DELETE",
  "entityType": "Sample",
  "entityId": "sample id",
  "reasonForChange": "required on data-altering ops (REPROCESS/UPDATE); project control mapped to 21 CFR Part 11",
  "signatureMeaning": "on REVIEW/APPROVE/SIGN, e.g. reviewed|approved|signed; project control mapped to 21 CFR Part 11",
  "detail": { "before": {"...": "optional, non-PII"}, "after": {"...": "optional, non-PII"} }
}

Omit reasonForChange and signatureMeaning when not applicable. Limit detail to non-PII status, method, instrument, and analyte values approved during project customization. Validate all event fields server-side.

DECOUPLED DELIVERY
- EventBridge PutEvents must return on the request path before downstream Firehose or S3 delivery completes; document this asynchronous boundary and its failure implications.
- Route the custom EventBridge bus through an EventBridge rule to Amazon Data Firehose and then Amazon S3.
- Configure and document an S3 error/backup prefix for failed delivery records.
- Add monitoring and tests for PutEvents failures and downstream delivery failures; do not claim zero loss without evidence.

DURABLE APPEND-ONLY STORAGE
- Configure the audit S3 bucket with versioning, a customer-managed KMS key for SSE-KMS, and S3 Object Lock.
- Grant Firehose PutObject-only S3 permissions and only the KMS permissions required to put encrypted audit objects; do not grant overwrite, delete, retention bypass, or broad read permissions.
- Enforce tenant-scoped reads.
- Make OBJECT_LOCK_MODE and OBJECT_LOCK_RETENTION_DAYS configurable from the approved customization record.
- Dynamic-partition Firehose output using this prefix structure: tenant_id=<id>/year=/month=/day=/...
- Explicitly document Object Lock creation constraints, retention behavior, legal hold considerations, and teardown consequences.

TENANT ISOLATION
- DynamoDB: isolate data by the tenantId partition key and require server-derived tenantId on every access.
- S3 and Athena: create a per-tenant IAM role that can read and list only its own S3 prefix, with explicit prefix conditions and equivalent Athena partition isolation.
- OpenSearch Serverless: use one tenant index named audit-events-<tenantId> and a per-tenant data access policy.
- Query Lambda: independently revalidate tenantId from the Cognito-authorized request before constructing any Athena or OpenSearch query.
- Prove with automated and demo checks that placeholder Tenant B is denied access to placeholder Tenant A's S3 prefix, Athena partition, and AOSS index. Use synthetic placeholder tenants only.

SEARCH
- Create an AWS Glue Data Catalog table and an Athena workgroup with partition projection.
- Structurally require a tenant_id predicate; do not rely only on caller discipline or query text instructions.
- Support filters for tenantId, actorId, operation, entity (represented by entityType), entityId, and timestamp range.
- Create an OpenSearch Serverless collection with one audit-events-<tenantId> index per tenant.
- Feed OpenSearch through an EventBridge-subscribed indexing Lambda.
- Apply per-tenant OpenSearch Serverless data access policies and approved network controls.
- Wrap Athena and OpenSearch Serverless behind the same Cognito-authorized API through a Query Lambda that revalidates the tenant.

REQUIRED ARCHITECTURE FLOW
Tenant User
  -> API Gateway (Cognito authorizer validates tenantId and sub)
  -> Sample Lambda
  -> DynamoDB write
  -> EventBridge PutEvents (asynchronous downstream delivery)
      -> EventBridge rule -> Firehose -> Object-Locked S3 -> Glue -> Athena
      -> EventBridge rule -> Indexing Lambda -> AOSS tenant index

Query path:
Tenant User
  -> API Gateway
  -> Query Lambda (independently revalidates tenant)
      -> Athena and/or AOSS

Use all four isolation layers: DynamoDB tenant partition; IAM plus S3 prefix conditions for Athena; one AOSS index per tenant; and application-layer tenant checks.

IMPLEMENTATION AND TEST EXPECTATIONS
- Keep the POC minimal and self-contained while implementing all four stacks and handlers in the required layout.
- Use least-privilege IAM and tightly scoped KMS policies. Keep S3 Block Public Access enabled and do not make the bucket, API, collection, or indexes public.
- Unit-test the shared event builder and operation rules, including server-set timestamp, JWT-derived tenant and actor, HTTP 422 behavior, omission of optional fields, non-PII detail validation, and exactly one audit event after each successful write.
- Add CDK unit or snapshot tests for versioning, Object Lock, SSE-KMS, retention configuration, Firehose permissions and prefixes, EventBridge routes, Cognito authorization, tenant-scoped IAM, Athena requirements, AOSS policies, RETAIN resources, logging, and alarms.
- Make scripts fail closed, use placeholder test data, and never embed credentials, account IDs, tenant/customer names, private endpoints, or PII.
- Document assumptions, failure handling, retry/idempotency design, and what can only be tested after an approved deployment.

PREDEPLOY VALIDATION
Pin exact dependency versions and review package identity, provenance, licenses, install scripts, lockfile changes, and vulnerability findings before installation. Run, in order:

Do not run cdk deploy without explicit confirmation from the owner of the named target AWS account. Object Lock retention can have irreversible consequences and retained resources can continue to incur cost. Run scripts/demo-walkthrough.sh only after an approved deployment.

SUCCESS CRITERIA
- A signed-in placeholder tenant action yields an event attributed to the JWT-derived actor and tenant.
- Decoupled delivery reaches immutable S3 without loss under the tested and documented conditions; report evidence and limitations rather than making an unsupported absolute claim.
- Cross-tenant reads are denied for S3 prefixes, Athena partitions, and AOSS indexes.
- A tenant can retrieve live audit events by actor, operation, entity, tenant, and time range through the authorized query API.

PRODUCTION HARDENING BEFORE AUDIT-GRADE USE
Produce a clearly unresolved checklist that requires project-owner review before production or audit-evidence use:
- Validate whether Object Lock COMPLIANCE mode is required. Use the owner-supplied example evaluation range of 365-2555 days only as an input to organization-specific legal, records, security, and compliance validation; do not select retention automatically.
- Do not grant s3:BypassGovernanceRetention.
- Apply RETAIN to the audit bucket and KMS key, and reconcile this with the approved teardown, cost, recovery, and data-disposition plan.
- Enable and protect S3 access logging and CloudTrail S3 data events.
- Use an approved AOSS VPC endpoint and network policy rather than public network access.
- Consider and, based on project review, prefer Lake Formation filters over IAM-plus-prefix isolation for Athena.
- Tighten KMS key administration and usage policy, enable rotation, and validate recovery ownership.
- Complete incident response, monitoring and alerting, backup/recovery, resilience, cost limits, data minimization, privacy review, threat modeling, change control, operational ownership, and independent compliance/security validation.
- Revalidate all control mappings and evidence with qualified project stakeholders; generated code and tests are not a compliance certification.
